# Dyad

Glue: engine/appbuild.mjs, engine/appjob.mjs, engine/export.mjs, engine/auto.mjs, engine/appkit.mjs, engine/systems.mjs, engine/advisor.mjs, engine/proc.mjs, engine/hermesllm.mjs
Status: built in

Dyad is a local AI app builder (dyad/README.md:3). Swarm vendors its agent engine in `dyad/`, copied from the owner's ABA fork (commit `8dd2d7a`), which adds a headless runner in `dyad/src/aba/` (dyad/SWARM.md:3-7). Licence: Apache-2.0 outside `src/pro/`, FSL-1.1-ALv2 inside it (dyad/README.md:33-34, dyad/LICENSE:1-3, dyad/src/pro/LICENSE:1-5). The agent tools below all live in `src/pro/` (dyad/src/pro/main/ipc/handlers/local_agent/tool_definitions.ts:150-209).

## What it already does

- Templates: React + Vite + shadcn + Tailwind (the default), Next.js, full-stack Vite + Nitro (experimental), and "Portal: Mini Store" with Neon, Payload CMS and Next.js (experimental, needs Neon) (dyad/src/shared/templates.ts:21-66).
- Agent mode ("local-agent") writes and edits files, adds npm packages, greps, searches code, reads logs, runs type checks, builds and tests, and spawns helper agents (dyad/src/pro/main/ipc/handlers/local_agent/tool_definitions.ts:150-209).
- Admin panels and dashboards are ordinary app code the agent writes. No special tool is needed. The owner confirmed Dyad builds them well (../DECISIONS.md:266, path from the repo root: `hermes hackathon/DECISIONS.md`).
- Tools that matter:
  - `web_crawl`: crawls a URL and clones the site from a screenshot plus markdown. It is used only when the person asks to clone/copy a site and gives a URL. Images become a grey placeholder (dyad/src/pro/main/ipc/handlers/local_agent/tools/web_crawl.ts:25-60).
  - `web_fetch` reads a page as markdown; `web_search` searches the web (tools/web_fetch.ts:45-94, tools/web_search.ts:18,175-184).
  - `add_integration`: asks the person to pick and set up Supabase or Neon, and blocks until they finish in Dyad's window (tools/add_integration.ts:14-35). Off in a headless run (see Limits).
  - `enable_nitro`: adds a Nitro server layer (`server/routes/api/`) to a Vite app. Enabled only for Vite apps without Supabase (tools/enable_nitro.ts:44-50; dyad/plans/nitro-integration.md:7,23-25).
  - `execute_sql` and `get_database_table_schema`: run SQL and read a table's schema on the linked Supabase, Neon or Octo database. Enabled only when one is linked (tools/execute_sql.ts:180-218, tools/get_database_table_schema.ts:31-58, tools/types.ts:395-415).
  - `get_supabase_project_info`, `get_neon_project_info` (tools/get_supabase_project_info.ts:23-28, tools/get_neon_project_info.ts:24-29).
  - `add_dependency`: installs npm packages (tools/add_dependency.ts:29-36).
  - `generate_image`: paints an image into `.dyad/media` (tools/generate_image.ts:30-141).
  - `planning_questionnaire`, `write_plan`, `exit_plan`, `write_app_blueprint`: Dyad's own planning flow. `write_plan`/`exit_plan` are plan-mode only. A blueprint needs a finished questionnaire first (tool_definitions.ts:663; tools/write_app_blueprint.ts:129-136). `planning_questionnaire` and `exit_plan` are off in a headless run (see Limits).
  - `search_mcp_tools`, `get_mcp_tool_schema`, `suggest_plugin`: MCP tools of the servers the person enabled (tools/search_mcp_tools.ts:67-77, tools/get_mcp_tool_schema.ts:35-46, tools/suggest_plugin.ts:236-251).
  - `view_render`: screenshots the running app (ABA addition; tools/view_render.ts:43-50).
- Stripe: Dyad has no Stripe integration. Its prompt only names "Stripe handlers" as server code (dyad/src/prompts/system_prompt.ts:347). A build adds `stripe` as a plain dependency.
- Plans in `dyad/plans/`, checked against this copy's code:
  - Neon (neondb-integration.md): shipped in part. `neon_admin/` and the Neon agent tools exist (dyad/src/neon_admin/neon_context.ts:147,331; tools/get_neon_project_info.ts:24). Unchecked: whether Neon works with the plain Next.js template; reading `dyad/src/ipc/utils/template_utils.ts` and the Neon connector would settle it.
  - Nitro (nitro-integration.md): shipped (tools/enable_nitro.ts:44-80).
  - Local Supabase (local-supabase-support.md): not shipped. No `supabase status` or local-instance detection in `dyad/src` (grep for `54321|supabase start|local supabase` finds only tests and remote-function sync code).
  - Convex (convex-backend-support.md): not shipped. No file in `dyad/src` mentions Convex.

## How Swarm drives it

- First use: `setupEngine` runs `pnpm install --frozen-lockfile` and `vite build --config vite.aba-headless.config.mts` into `dyad/.vite/build/aba_headless.cjs`, on a Node in dyad's `engines` range (engine/appbuild.mjs:135-163).
- `runEngine` spawns `node aba_headless.cjs --prompt <file> --workspace <app> --model <m> --gateway <baseUrl> --turns N --user-data-dir <dir> --json --view-render` (engine/appbuild.mjs:60-66,196). Its env is only git, `appEnv()`, `ABA_API_KEY` (the studio's own /llm/v1 key), `ABA_ENV_FILE` (a missing file, so no `.env` is read) and `ELECTRON_RUN_AS_NODE` (engine/appbuild.mjs:205-212).
- The bundle follows Dyad's source: `sourceStamp` hashes every file under `dyad/src`, the bundle's vite config and the lockfile, and `setupEngine` writes it beside the bundle (`aba_headless.cjs.stamp`) after a build that succeeded. A bundle with another stamp, or none (one built before stamps), is installed-checked and bundled again the next time the engine is used ("updating the app engine", about 30 s here), never while an engine process runs. If that fails, the engine that was there keeps building (engine/appbuild.mjs:27-43,135-163). An update that cannot be made (no fitting Node, no pnpm, a bundle error) is not tried again until the Studio restarts (engine/appbuild.mjs:139-140,157-161). Before this, the bundle was built once and a changed runner was never picked up.
- Chat modes. Dyad has four: `build`, `ask`, `local-agent`, `plan` (dyad/src/lib/schemas.ts:177). The runner takes `--mode <mode>`, default `local-agent` (dyad/src/aba/headless_args.ts:100-221), and hands it to each turn as `requestedChatMode` (dyad/src/aba/headless_cli.ts:335-349); the requested mode wins over the chat's stored one (dyad/src/ipc/handlers/chat_mode_resolution.ts:37-38). `runEngine` passes `--mode` only when it is not the default, so a bundle from before the flag still builds (engine/appbuild.mjs:52-58).
  - `local-agent` and `build`: the gate loop described below. Swarm uses `local-agent` for every build. Unchecked: `build` (Dyad's older tag-writing mode) headless.
  - `ask` and `plan` are one turn on an existing `--workspace`: no dependency install, no typecheck or build gates, no repair turns, no `RUN_META.json`. They refuse `--out`, `--scaffold`, and a folder without `package.json` and `.git` (so nothing is seeded or committed). The JSON result is `{ ok, chatMode, turns: 1, answer, changed, … }`: `answer` is the last assistant message without Dyad's own tags and `<think>` blocks (`cleanAnswer`), and `changed` is the app's git saying whether anything moved (dyad/src/aba/headless_cli.ts:198-209,368-412; dyad/src/aba/headless_args.ts:209-218,224-232).
- Ask (Swarm's Ask mode for a built app or game, docs/specs/46-chat-modes.md): `appJobs().ask(runId, text)` runs one `--mode ask` turn with the builder model on the run's app, in the same engine chat as its builds, so the question and answer are in the builder's history afterwards (engine/appjob.mjs:217,882-897; route `POST /api/runs/<id>/app/ask`, server/server.mjs:1510-1529). Dyad's ask mode is its agent with `readOnly`: its own "understand the app" prompt, and every state-changing tool dropped (dyad/src/ipc/handlers/chat_stream_handlers.ts:2778-2822; tool_definitions.ts:794-801); no auto-approve commit (chat_stream_handlers.ts:3206). It is refused while that app builds or another Studio builds it (the crew's Talk answers then), one question at a time per app, and a build of that app waits for the answer. With no engine installed or no app built it returns no answer and the caller uses Talk or the planner: a question never installs the engine.
  - Checked 2026-11-14 with the runner built from this source and a stand-in gateway that scripts the model's replies (no real model): the ask turn was offered 20 read-only tools (`read_file`, `list_files`, `grep`, the git readers, `read_logs`, `run_type_checks`, `spawn_agent`, `web_search`, `web_fetch`, `web_crawl`, `execute_sandbox_script` and others) and no writer, ran a scripted `list_files`, answered, and left `git status` and `git log` as they were, in about one second. Unchecked: a real model's answers.
- The runner boots Dyad in-process with Pro on and no Pro key, agent mode, auto-approve, all subagents on, and `execute_sql`, `add_dependency`, `web_search`, `web_crawl` set to "always" (dyad/src/aba/headless.ts:124-135,428-453). It streams the prompt, then runs the app's `typecheck` (if the script exists) and `build`, and sends failures back as repair turns until `--turns` runs out (dyad/src/aba/headless_cli.ts:79-125,414-432). It prints one JSON line `{ ok, gatesPassed, turns, files, commits, egressHosts, ... }` and writes `RUN_META.json` (dyad/src/aba/headless_cli.ts:451-483). `runEngine` parses that line (engine/appbuild.mjs:239,247).
- Which template Swarm seeds: the bare `dyad/scaffold/` (Vite + React + shadcn; dyad/scaffold/package.json:2-11), copied by `seedProject` (engine/export.mjs:314-322). For a site, `dyadApp` writes the design's sections and pages into it and removes `made-with-dyad.tsx` (engine/export.mjs:324-331). The scaffold has no `typecheck` script, so only `build` gates (dyad/scaffold/package.json:6-12; dyad/src/aba/headless_cli.ts:79-125). Swarm never picks Next.js, Nitro or Portal as a template.
- What Swarm's prompts dictate (engine/appjob.mjs):
  - keep the converted design's markup, classes and CSS variables (`KEEP`, :24);
  - call `enable_nitro`, put routes in `server/routes/api/`, keep data in a typed server-side store (`BACKEND`, :32-34);
  - sign-in is Supabase Auth when `SUPABASE_URL` is set, else a labelled scrypt guest pass, and no unconfigured provider buttons (`AUTH`, :27-30);
  - forms with zod + react-hook-form, GET routes for lists, saved records, and an `/admin` page with a shadcn Table and a summary unless a plan names the back office (`sitePrompt`, :47-71).
- What is left to Dyad: how to write the code, which files and packages, how the admin screens and dashboards look and work, and the repair loop (the prompts above dictate nothing else: engine/appjob.mjs:24-71; the repair loop is dyad/src/aba/headless_cli.ts:414-432).
- More prompts: Auto mode's games, `SHOP_ASK` checkout and `supabaseAsk` (engine/auto.mjs:59,82-89,217,267). The advisor's back-office questions (engine/advisor.mjs:22-36). The App kit's locked plan, `kitPlan` (engine/appkit.mjs:313-331). Systems modules (engine/systems.mjs:44-60).
- Swarm then serves the app itself on 127.0.0.1 and deploys it to Vercel (`deploy`). How it serves it (decision 0017, issue #450, spec 44 "the dev server only while building"):
  - While the crew builds or someone edits: the app's Vite dev server (`serve`, engine/appjob.mjs), started with execa through `start()` (engine/proc.mjs, engine/vendor/procs/).
  - Once building stops: the app built (`serveBuilt`). `vite build` runs when the app's files changed since the last build (`sourceSig`, stamped in `.swarm-built.json`), then `dist/` is served as files from Swarm's own process, with a fallback to `index.html` (engine/godotfirst.mjs `serveStatic`). An app with server routes (Dyad's Nitro layer: `nitro.config.ts` or `server/`) builds to `.output/` and runs as `node .output/server/index.mjs`, the start command Dyad itself writes (dyad/src/lib/framework_constants.ts:58), behind a front that adds CORS for the sandboxed frame (`corsFront`).
  - Either server stops after 2 minutes with no viewer and no build (the App view's heartbeat, `POST /api/runs/<id>/app/seen`; Settings › Background), and at most 2 run, the least recently viewed stopped first (engine/lifecycle.mjs `previewPool`). A stop kills the whole process tree (`stopTree`, tree-kill). Opening it again serves it cold, with the App view's skeleton while it starts.
  - A big game waiting after a slice ("your turn") is stopped the same way, and is not an app yet (`hasApp` needs a finished build). Its state says `canServe` when its files are there, the App view opens it again when the person asks (the Live option, Play it live, "show the game": `POST /api/runs/<id>/app/open`, served built), and it stays `paused` with its slice (engine/appjob.mjs `open`, `servable`; tests/elsewhere.test.mjs). Unchecked: a real `vite build` of a slice whose play test failed; the test uses an already built `dist/`.
  - Unchecked: a real `vite build` of a Nitro app here; the Nitro start command and `.output/` come from Dyad's code, not from a run.
- What Swarm keeps for the app build wall (spec 44):
  - The plan an app was built from (the advisor's, or a locked App kit's through `kitPlan`), without its keys, as `runs/<id>/app-plan.json` (`start`, engine/appjob.mjs). `GET /api/runs/<id>/app/map` gives it as Mermaid text, a flowchart of the screens and an ER diagram of the data (engine/appmap.mjs), or `null` when the run kept no plan.
  - One photo of the built app, `runs/<id>/img/app.jpg`, taken once it is served built (`photo`, engine/appjob.mjs), with the play test's browser (engine/playtest.mjs `launch`: Playwright's, an installed Chrome or a shell already there; never a download). Dyad's own `view_render` keeps no picture: it attaches its JPEG to the model's message only (dyad/src/pro/main/ipc/handlers/local_agent/tools/view_render.ts:97-113).

- A project brought in from outside ([spec 45](../specs/45-intake.md), engine/bringin.mjs, engine/appjob.mjs `bring`) is never seeded or built over: `start` refuses a first build or a start over on it. What a follow-up does depends on its shape:
  - Plain files (no `package.json`): refused before the engine is called. The runner's gate reports a workspace with no `package.json` as `"no package.json: the workspace is not an ABA app"`, origin `foreign`, `ok: false` (dyad/src/aba/headless_cli.ts `runGates` and the `workspaceOrigin` block below it), and `serve` would then run `pnpm install` and Vite on it. Read from the code, not from a run. The runner's `--adopt-reason <text>` records such a workspace as `adopted` with `ok: true` (dyad/src/aba/headless_cli.ts:16, 435-449); Swarm does not pass it yet.
  - A Vite project: the ask goes to `runEngine` with a prompt of its own ("made outside this tool … keep its structure, tools and style"), not `KEEP` or `BACKEND`. Unchecked: no real engine turn has been run on a brought-in project; one run on a small Vite project would settle it.
  - Its install, build, dev server and built server get no app keys (engine/appjob.mjs `appEnvFor`), and `runEngine` is called with `appKeys: false`, so `appEnv()` is left out of the engine's environment for it (engine/appbuild.mjs); tests/bringin.test.mjs "code from outside is never handed the person's keys".
  - It is installed with `pnpm install --prefer-offline --ignore-scripts` (engine/appjob.mjs `installArgs`). Measured 2026-11-13 with pnpm 12.14.0 on a bare Vite 5 project: without `--ignore-scripts` the install fails with `ERR_PNPM_IGNORED_BUILDS` (esbuild's build script); with it, `vite build` runs and `dist/` is served.

## What the person connects

- Models: nothing for Dyad itself. The gateway is the studio's `/llm/v1`, forwarded to Hermes (engine/hermesllm.mjs:1-6). Or `SWARM_STUDIO_API_KEY` / `SWARM_STUDIO_BASE_URL` when set (server/server.mjs:115-128, plugin.yaml:12-13).
- App data: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (plugin.yaml:41-44), or Hermes's Supabase connector (docs/specs/25-connections.md:30). The table `swarm_records` is made once by the person (engine/auto.mjs:62,75).
- Payments: `STRIPE_SECRET_KEY`, test keys only. A live key is never handed to an app (engine/proc.mjs:32-37, plugin.yaml:46-48).
- Email: `RESEND_API_KEY`, handed only to an app whose locked kit chose Resend (engine/proc.mjs:31-36, engine/appkit.mjs:390).
- Disk: the first app build installs about 1.5 GB into `dyad/node_modules` (README.md:217).

## Limits inside Swarm

- Egress guard: `installEgressGuard` wraps `fetch` in the engine process and refuses any host but the gateway, the image host and the Octo host (Octo only when `OCTO_*` keys are set). Loopback is allowed with `--view-render` (dyad/src/aba/headless.ts:327-383; dyad/src/aba/headless_cli.ts:221-248). Every dyad.sh URL points at a dead loopback port (dyad/src/aba/headless_env.ts:19-28).
- Clone, web search, web fetch and image tools do not work in Swarm today. They call `DYAD_ENGINE_URL` + `/tools/web-crawl`, `/tools/web-search`, `/images/generations` (tools/web_crawl.ts:91, tools/web_search.ts:108, tools/web_fetch.ts:68, tools/generate_image.ts:64). The runner sets `DYAD_ENGINE_URL` to the gateway (dyad/src/aba/headless.ts:301-304). Swarm's `/llm/v1` serves only `chat/completions` and `models` and answers 404 to the rest (engine/hermesllm.mjs:22,37-41). Swarm paints pictures with its own pipeline instead (engine/appjob.mjs:143-146,327). Unchecked: whether the tools work with `SWARM_STUDIO_BASE_URL` pointed at a gateway that serves those paths. The first piece is in: the bridge's `POST /web` reaches Hermes's own `web_search` and `web_extract` (bridge.py, docs/engines/hermes-and-connections.md). The three gateway routes that would answer Dyad's tools from it are not built (PR 382 lists what they need).
- Dyad's own database setup cannot run here. `add_integration` waits for a person in Dyad's desktop window, which the headless runner does not have, so it is off (next point). `execute_sql` and the schema tools need a linked Supabase/Neon project (tools/add_integration.ts:27-33; tools/types.ts:395-415). Swarm wires Supabase through prompts and env instead (engine/auto.mjs:59; engine/proc.mjs:32-37). The app's own runtime calls to Supabase or Stripe run in the app's Vite process, not under the guard (engine/appjob.mjs:631).
- Nobody answers Dyad's own questions in a headless run, so the tools that ask are off (fixed 2026-11-14; before it, a build whose model called one died). Five tools wait for a person: each parks a request with `userInputRegistry.park` that only an answer from Dyad's window, a deadline or an abort settles (dyad/src/user_input/registry.ts:367-399), and the runner has no window. They are `planning_questionnaire`, `add_integration`, `suggest_plugin`, `exit_plan` and `generate_test_assertions` (tools/planning_questionnaire.ts:166, add_integration.ts:87, suggest_plugin.ts:319, exit_plan.ts:93, generate_test_assertions.ts:397).
  - What happened before, checked 2026-11-14 with the runner built from this source and a stand-in gateway scripting the tool call (no real model): on `planning_questionnaire` (no deadline, registry.ts:121-128) nothing kept the process alive, so the runner exited at once with code 0 and no result line, and `runEngine` reported "the app engine exited (0) without a result" followed by two engine log lines every run prints. The tool is offered in agent mode too (tool_definitions.ts:660-663), so a build ended that way, not only plan mode. On `add_integration` the run did not end: it waited (stopped by hand after 3 minutes 40 seconds; the request's deadline is 30 minutes, registry.ts:34,123).
  - Now the runner's boot sets all five to consent "never" (`HEADLESS_OFF_TOOLS`, dyad/src/aba/headless_args.ts:17-35; dyad/src/aba/headless.ts:124-135), which is Dyad's own switch: a "never" tool is left out of the turn (`shouldIncludeTool`, tool_definitions.ts:743-745) and the blueprint steps of the prompt read the same setting (dyad/src/ipc/handlers/chat_stream_handlers.ts:2228-2229). The model plans with what it has.
  - A model that calls one anyway gets Dyad's own refusal as the tool's result ("Model tried to call unavailable tool 'planning_questionnaire'. Available tools: …") and the turn goes on. After a refused `planning_questionnaire` Dyad also adds a message of its own, once a turn: in agent mode "Skip the questionnaire step and proceed directly to the planning phase", in plan mode "re-call planning_questionnaire with correct arguments", which would be refused again (local_agent_handler.ts:1643-1660,2809-2820; the agent-mode one seen in the stand-in run). Dyad's prompt still names two of them whatever the setting: the Clarify step says to use `planning_questionnaire`, and a Vite app's server-layer block says to call `add_integration` before `enable_nitro` when a database is needed (dyad/src/prompts/local_agent_prompt.ts:305,501-512). So `runEngine` ends every build or plan prompt with a line saying nobody is here and those tools are not available (`ALONE`, engine/appbuild.mjs:59-62).
  - Dyad ends a turn on any `add_integration` call, refused or not, and on `exit_plan` in plan mode (`stopWhen`, local_agent_handler.ts:1454-1473); in its window a hidden "continue" follows once the person is done. The runner does that part: a turn whose last word is a refused call to one of the five (`offToolStop`, dyad/src/aba/headless_args.ts:37-56) is followed by a turn that says "Nobody is here to answer … decide for yourself … and go on", at most twice for one ask (dyad/src/aba/headless_cli.ts:350-366). It counts as a turn in the result's `turns`, and the App tab shows the step "nobody to ask: deciding alone" (`stepOf`, engine/appbuild.mjs:169).
  - Checked 2026-11-14 the same way (tests/headlessasks.test.mjs, run against the bundle built from this source): a scripted build that calls `planning_questionnaire`, then `add_integration`, then writes a file ends with `ok: true`, gates passed, the file written, `turns: 2`, and none of the five among the tools offered; a scripted plan-mode turn that calls `planning_questionnaire` ends with its answer. CI has no engine installed, so there those two tests are skipped; the test that every tool that parks is in `HEADLESS_OFF_TOOLS` runs everywhere, and fails when Dyad gains a sixth. Unchecked: a real model's behaviour, and `suggest_plugin`, `exit_plan` and `generate_test_assertions` each called for real (read from their code; `generate_test_assertions` first needs a recording made in Dyad's window, tools/generate_test_assertions.ts:117).
  - If an engine process still ends with no result line, the Studio says "The app engine stopped before it finished", with the engine's last error line when it gave one of its own; the exit code goes to the run's `.engine/engine.log` (`noResult`, `logTail`, engine/appbuild.mjs:248-266).
- Dyad's plan mode is not used by Swarm. Plan mode is the agent with `planModeOnly` and a prompt whose job is to gather requirements first (chat_stream_handlers.ts:2824-2870); headless its tools are the read-only set plus `write_plan` (the questionnaire and `exit_plan` are off, above). `write_plan` works headless: it wrote `.dyad/plans/chat-1-plan.md` (front matter: title, summary, status draft) and added `.dyad` to the app's `.gitignore`, and the turn ended there with no words (tools/write_plan.ts:74-98; dyad/src/ipc/handlers/planPersistence.ts:68-70,102-128; seen in the stand-in run before the fix). The runner's `--mode plan` exists and reports the plan files it finds (`plans`), but Swarm's Plan mode is the planner's talk for apps and games too (docs/specs/46-chat-modes.md). For Dyad's plan mode to ask the person its questions, the runner would need to pass Dyad's user-input requests to Swarm's chat and back; it answers none today.
- `write_app_blueprint` is off: the headless app row keeps `needs_app_blueprint` at its default 0 (dyad/src/db/schema.ts:122-124; dyad/src/pro/main/ipc/handlers/local_agent/local_agent_handler.ts:1143-1144).
- MCP: the headless boot adds no MCP servers, and the MCP catalog URL is dead (dyad/src/aba/headless.ts:456-532; dyad/src/aba/headless_env.ts:25). Unchecked: whether Hermes's MCP servers could be added as rows.
- Licence: `src/pro/` is FSL. Non-commercial and internal use is fine (dyad/SWARM.md:9-11). A Competing Use is not allowed (dyad/src/pro/LICENSE:30-32).
- No Dyad branding in built apps (../DECISIONS.md:131; engine/export.mjs:318-321,330).
